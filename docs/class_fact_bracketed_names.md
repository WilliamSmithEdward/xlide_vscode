# Bracketed names in class-value diagnostics

The class-fact scanner treated only ordinary identifier tokens as field/result references. A class constructor assigning `Set Me.[member] = New Collection` was therefore reported as never setting its Object field. The equivalent unbracketed spelling produced no diagnostic. Bracketed Function/Property Get result assignments also looked unassigned, producing incorrect Nothing/Empty hints.

The fact scanner now uses the shared token-name decoder for identifiers and bracketed identifiers. Raw keyword/operator matching remains separate: `[If]` is a name, not an If statement. Earliest/latest mention indexing and bounded body scans remain in place. The consuming diagnostic rule decodes member names consistently for reads and field-assignment suppression, and recognizes bracketed instance names when checking whether the local instance escapes to another procedure. Original display text and exact source spans remain intact.

Validation on baseline `3c8725d531173a6e5b209402e581074bd7a2455d`: 36 of the 43 new tests fail and seven controls pass. Repaired type checking, 63 focused tests and the full suite pass (779 files / 15,268 tests; 7 files / 33 tests skipped; 74.53 seconds). Tests cover Object/Variant fields, Function/Property Get results, Nothing controls, Unicode and keyword-shaped names, string/comments, complete reads, assignment suppression and instance escape across LF/CRLF/CR.

The frozen comparison checks complete fact maps, project-member metadata and caller diagnostics/internal failures on all 8,247 oracle sources without bracketed-identifier tokens across three line endings: 24,741 queries, zero differences. Nine bracketed sources are excluded from compatibility equality because their behavior may intentionally change. Independently expected facts for 5,000 generated bracketed classes match equivalent ordinary identifiers. This is a correctness repair discovered during the performance audit; no timing, heap or editor improvement is claimed.
